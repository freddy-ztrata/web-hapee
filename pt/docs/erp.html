Integre seu ERP com a Hapee

Os fluxos completos, o mapeamento de campos e o checklist de saída. Escrito para ser suficiente sem a gente ao seu lado.

Antes de escrever uma linha

Três coisas que definem todo o resto:

  1. A subconta vem da credencial. Nunca é enviada como parâmetro. Uma credencial pertence a uma subconta e só pode ler e escrever nela.
  2. Há duas formas de saber o que acontece e ambas entregam exatamente o mesmo: webhooks (nós avisamos) ou GET /events (você consulta). Você escolhe conforme seu ERP possa ou não expor uma URL pública, não conforme o que quer receber.
  3. Toda escrita aceita Idempotency-Key. Uma nova tentativa por queda de rede não duplica nada. Use desde o primeiro dia, não quando o problema aparecer.
curl https://beta.hapee.ai/api/v1/me \
  -H "Authorization: Bearer hp_test_SUA_CREDENCIAL"

Se isso funciona, o resto funciona.

API ou workflows?

Há três formas de conectar e elas não competem: são usadas juntas. A diferença real é quem escreve o código.

O que você quer fazerCaminhoQuem faz
Carregar milhares de empresas, contatos e produtosOs três lotes da APISua equipe técnica
«Negócio ganho → avisar o ERP»WorkflowSua equipe comercial, sem código
«O ERP avisa que foi pago»Gatilho de webhookUma chamada HTTP, sem credencial

Com workflows, sem escrever código do lado da Hapee

Dentro da Hapee, no construtor de workflows, há duas peças que conversam com seu sistema:

  • Nó «Webhook de saída» — colocado depois da etapa que lhe interessa (por exemplo, «o negócio passou para Ganho») e faz um POST para sua URL. Configuram-se a URL, o método, o corpo JSON com variáveis do contato, os headers e um segredo para assinar.
  • Gatilho «Webhook recebido» — dá a você uma URL para a qual seu sistema faz POST para iniciar o workflow. Não precisa de credencial: basta o token que vai na própria URL.

É o caminho mais rápido para começar: quem já usa a Hapee monta em uma tarde, sem esperar por ninguém.

⚠️ Um 4xx do seu lado NÃO interrompe o workflow. O motor só tenta novamente quando seu sistema responde 5xx. Se ele responde 401 porque o token está errado, ou 400 porque não gostou do corpo, o workflow segue como se tivesse funcionado e ninguém percebe.

O código de resposta fica na variável _http_status. Coloque sempre um nó «Se / Senão» que o verifique logo após o webhook de saída, e envie o caso ruim para uma notificação interna. Sem isso, no dia em que seu token vencer, as vendas «foram avisadas» e não chegaram.

No registro de execução do workflow essa etapa aparece marcada como «sem efeito», com o código HTTP ao lado — mas isso só vê quem entra para olhar, e o nó «Se / Senão» avisa sozinho.

Fonte da verdade: quem manda em quê

É preciso combinar isto antes de sincronizar qualquer coisa, porque define o que acontece quando os dois lados alteram o mesmo dado. A proposta padrão:

EntidadeMandaMotivo
Dados tributários (RUT, razão social, ramo de atividade)ERPÉ o que vai no DTE
Produtos e preços de listaERPÉ onde o catálogo é mantido
Faturas, notas de crédito, pagamentosERPO SII só conhece o ERP
Etapa do negócio, atividade comercialHapeeÉ onde a equipe de vendas trabalha
Contatos e seu histórico de conversasHapeeÉ onde elas acontecem
Dados de contato (telefone, e-mail)Quem mexeu por últimoOs dois são válidos

O que não pode acontecer é não decidir. Sem este acordo, cada lado sobrescreve o outro e o sintoma aparece semanas depois como «os dados somem».

Fluxo A — Carga inicial

Uma única vez, ao conectar. Não existe POST /{recurso}/batch. O contrato OpenAPI 3.1 publicado em beta.hapee.ai/api/v1/openapi.json tem lote em exatamente três rotas, e elas não compartilham forma nem limite:

RotaLimiteCada itemResposta 200
POST /companies/batch1 a 100Upsert de empresaEsquema LoteResultado
POST /contacts/batch1 a 100Upsert de contatoEsquema LoteResultado
POST /products/batchaté 500Upsert por skuSem esquema publicado

Categorias de produto, negócios, cotações, registros de objetos custom e o restante dos recursos são carregados um a um, com o POST ou upsert daquele recurso. Não há POST /product-categories/batch, POST /deals/batch nem um lote montado com o nome do recurso.

Empresas e contatos

O corpo é { "items": [ … ] }. items é obrigatório (minItems: 1, maxItems: 100). Cada elemento é o mesmo corpo de POST /companies/upsert ou POST /contacts/upsert. Um campo que esse esquema não reconhece é ignorado. Com uma credencial já limitada a uma subconta, não envie cliente_id: se vier e não coincidir, a API o ignora ou responde 404. Só é obrigatório com credencial de agência e, nesse caso, vai no lote: o cliente_id de cada item é substituído pelo do lote.

Um item ruim não aborta o lote. A chamada responde 200 mesmo assim. O item que falhou traz error com o detail que o upsert avulso teria devolvido, e results[].status é o código desse upsert. created: false significa que já existia e foi atualizado. Os resultados voltam na mesma ordem de items.

curl -X POST https://beta.hapee.ai/api/v1/companies/batch \
  -H "Authorization: Bearer hp_test_SUA_CREDENCIAL" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: carga-inicial-empresas-lote-001" \
  -d '{
    "items": [
      {"external_id": "ERP-CLI-4471", "rut": "76.543.210-K",
       "nombre": "Comercial Andes SpA",
       "email": "contacto@andes.cl"},
      {"external_id": "ERP-CLI-4472", "rut": "77.111.222-3",
       "nombre": "Distribuidora Sur Ltda"}
    ]
  }'
{
  "job_id": 812,
  "total": 2, "succeeded": 2, "failed": 0,
  "results": [
    {"index": 0, "ok": true, "status": 201, "created": true, "data": {"id": 9001}},
    {"index": 1, "ok": true, "status": 201, "created": true, "data": {"id": 9002}}
  ]
}

POST /contacts/batch usa o mesmo envelope e a mesma resposta. O que muda é cada item: campos de contato (external_id, email, first_name, phone, company_id, …). O pareamento de contatos é external_id, depois rut, depois email, depois phone. O de empresas é external_id, depois rut, depois email: o telefone não identifica uma empresa. match_by fixa um único critério; se não houver coincidência, o registro é criado e o pareamento não cai para o seguinte.

Um RUT que não valida não derruba a chamada. Fica assim dentro de results:

{
  "index": 1, "ok": false, "status": 422,
  "error": {
    "code": "validation_error",
    "message": "El RUT no es válido.",
    "details": [{ "field": "rut", "issue": "invalid_check_digit" }]
  }
}

Erros que rejeitam a chamada inteira

Em POST /companies/batch e POST /contacts/batch o contrato declara estes códigos para a chamada, antes de processar itens:

  • 401 — credencial ausente, inválida ou vencida.
  • 403 — a credencial não pode fazer a chamada: permissões, IP ou sandbox.
  • 409 — a Idempotency-Key foi reutilizada com outro corpo, ou a mesma chave ainda está em andamento. A chave é opcional, de até 255 caracteres, com janela de 24 horas. A mesma chave e o mesmo corpo devolvem a resposta original com Idempotent-Replay: true.
  • 429 — chamadas demais. Espere o que diz Retry-After.

Fora de 1 a 100 itens o corpo não cumpre o esquema e o lote não roda. Um item inválido não usa estes códigos: fica em results[].error e o HTTP continua 200.

Produtos

POST /products/batch cria ou atualiza até 500 produtos. Pareia por sku, obrigatório em cada um: carregar de novo o mesmo SKU atualiza em vez de duplicar. Cada item leva sku e nombre, e pode levar descripcion_corta, descripcion_html, imagen_url, unidad, tipo, estado (activo ou inactivo), categoria (o nome; é criada se não existir), precios ({"CLP": {"precio", "precio_min", "costo"}, "USD": {…}}) e campos_custom (chave e valor; a propriedade é criada se não existir).

Campos de um item, como o texto da operação os nomeia. O OpenAPI não publica o esquema do corpo nem o da resposta 200: não reutilize job_id nem results[] de empresas e contatos.

{
  "sku": "AND-100",
  "nombre": "Filtro de aire",
  "estado": "activo",
  "categoria": "Repuestos",
  "precios": { "CLP": { "precio": 12990, "precio_min": 11990, "costo": 8000 } },
  "campos_custom": { "bodega": "SCL-01" }
}

Os erros de chamada que esta rota declara são 401, 403, 409 e 429, com o mesmo significado. As categorias que você quiser criar à parte vão uma a uma com POST /product-categories.

Três coisas que poupam uma dor de cabeça

  • Em empresas e contatos, envie sempre external_id com o id do seu ERP. É o que permite repetir a carga sem duplicar: a segunda execução atualiza em vez de criar ("created": false). Em produtos a chave é o sku, não o external_id.
  • O job_id de LoteResultado permite reler o resultado com GET /jobs/{job_id} se você perder a resposta do lote de empresas ou contatos. Essa rota devolve o estado do trabalho e, quando terminou, o resultado por item. O POST já traz esse resultado no 200: o job é a cópia guardada. GET /jobs lista trabalhos (status e limit, 50 por padrão). O contrato de POST /products/batch não publica job_id: não releia essa chamada com GET /jobs/{job_id}.
  • Carregue empresas antes dos contatos, para poder associá-los com company_id (o id da Hapee, não o do seu ERP).

Ordem recomendada: POST /companies/batch, depois as categorias avulsas com POST /product-categories e o catálogo com POST /products/batch, e por fim POST /contacts/batch.

Fluxo B — Sincronização incremental

ERP → Hapee

Use upsert, não create. O pareamento é a parte delicada e a precedência é determinística:

external_id  >  rut  >  email  >  phone

Testa-se um critério por vez, em ordem, e vale o primeiro que encontrar algo. Você pode fixá-lo com match_by:

curl -X POST https://beta.hapee.ai/api/v1/contacts/upsert \
  -H "Authorization: Bearer hp_test_SUA_CREDENCIAL" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: sync-contato-CON-991-v3" \
  -d '{
    "match_by": "external_id",
    "external_id": "ERP-CON-991",
    "email": "jefe.compras@andes.cl",
    "first_name": "Rodrigo", "last_name": "Pinto",
    "phone": "+56912345678",
    "custom_fields": {"payment_terms": "30 días"}
  }'

match_by é exclusivo. Se você pede para parear por external_id e não há correspondência, ele cria — não recorre ao e-mail. É de propósito: recorrer seria desobedecer você justamente quando foi explícito, e poderia sobrescrever alguém que seu ERP considera outra pessoa.

O RUT é validado. Um dígito verificador errado retorna 422 e nada é salvo. Um RUT mal salvo não identifica ninguém e além disso envenena toda deduplicação futura: a próxima carga com o RUT correto não o encontra e cria uma duplicata.

Hapee → ERP

Duas opções, os mesmos dados. Opção 1 — Webhooks (recomendada se você puder expor uma URL https):

curl -X POST https://beta.hapee.ai/api/v1/webhooks/endpoints \
  -H "Authorization: Bearer hp_test_SUA_CREDENCIAL" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://erp.suaempresa.com.br/hooks/hapee",
    "description": "ERP produção",
    "events": ["deal.won", "quote.accepted", "contact.updated", "company.updated"]
  }'

A resposta traz o secret uma única vez. Veja Webhooks para a verificação de assinatura.

Opção 2 — GET /events (se o ERP está instalado na empresa, sem porta aberta):

curl "https://beta.hapee.ai/api/v1/events?cursor=10432&limit=100" \
  -H "Authorization: Bearer hp_test_SUA_CREDENCIAL"
{
  "data": [
    {"id": "evt_10433", "type": "deal.won", "api_version": "v1",
     "created_at": "2026-09-10T14:02:11Z", "subaccount_id": 63,
     "data": {"id": 5521, "title": "Reposição Q4",
              "amount": "4200000", "currency": "CLP"}}
  ],
  "next_cursor": "10433",
  "has_more": false
}

Guarde o next_cursor e passe-o na chamada seguinte. Os eventos vêm do mais antigo ao mais novo de propósito: você está se atualizando, e é preciso processar na ordem em que ocorreram. Retenção: 30 dias.

Fluxo C — Negócio ganho → fatura

O fluxo que justifica a integração.

  Hapee                          Seu ERP
    │
    │  A equipe marca o negócio como ganho
    │
    ├──── deal.won ─────────────────►│
    │     (webhook ou /events)       │
    │                                │  Cria o pedido de venda
    │                                │  Emite o DTE junto ao SII
    │                                │
    │◄─── PATCH /deals/{id} ─────────┤  Escreve o folio de volta
    │       invoice_number: "F-8842" │
    │       payment_status: "pending"│
    │                                │
    │◄─── POST custom-objects/…  ────┤  Publica o documento como
    │                                │  registro visível no CRM
    │
    │  O executivo VÊ a fatura dentro da ficha do cliente

Passo 1 — Você recebe o evento

deal.won traz o negócio completo, com o mesmo formato que GET /deals/{id} retorna.

Passo 2 — Você escreve de volta

curl -X PATCH https://beta.hapee.ai/api/v1/deals/5521 \
  -H "Authorization: Bearer hp_test_SUA_CREDENCIAL" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: folio-F-8842" \
  -d '{"custom_fields": {
        "invoice_number": "F-8842",
        "payment_status": "pending",
        "due_date": "2026-10-10"}}'

Passo 3 — Você publica o documento como registro

Assim o executivo vê a fatura sem sair da Hapee:

curl -X POST https://beta.hapee.ai/api/v1/custom-objects/{objeto_id}/records \
  -H "Authorization: Bearer hp_test_SUA_CREDENCIAL" \
  -H "Content-Type: application/json" \
  -d '{
    "external_id": "ERP-DTE-8842",
    "values": {
      "folio": "F-8842", "tipo_dte": "33",
      "monto_neto": "3529412", "iva": "670588", "total": "4200000",
      "moneda": "CLP", "fecha_emision": "2026-09-10",
      "estado": "emitida",
      "url_pdf": "https://erp.suaempresa.com.br/dte/8842.pdf"
    }
  }'

Fluxo D — Cobrança

# 1. O ERP avisa que o documento venceu sem pagamento
curl -X PATCH https://beta.hapee.ai/api/v1/deals/5521 \
  -H "Authorization: Bearer hp_test_SUA_CREDENCIAL" \
  -d '{"custom_fields": {"payment_status": "overdue", "amount_paid": "0"}}'

# 2. O contato é etiquetado
curl -X POST https://beta.hapee.ai/api/v1/contacts/8821/tags \
  -H "Authorization: Bearer hp_test_SUA_CREDENCIAL" \
  -d '{"tag": "cobranza-vencida"}'

# 3. O contato é inscrito no workflow de cobrança
curl -X POST https://beta.hapee.ai/api/v1/workflows/44/enroll \
  -H "Authorization: Bearer hp_test_SUA_CREDENCIAL" \
  -d '{"contacto_id": 8821}'

A partir daí, a Hapee cuida de tudo: os lembretes, o WhatsApp, o e-mail. Quando o cliente paga, o ERP fecha o ciclo com payment_status: "paid" e a etiqueta é removida.

Checklist para ir à produção

Antes de trocar hp_test_ por hp_live_:

  • GET /me responde e mostra a subconta correta
  • A carga inicial foi executada duas vezes no sandbox e não duplicou nada
  • Empresas e contatos têm external_id com o id do seu ERP; cada produto tem sku
  • Os RUTs que não validam ficam em results[].error do lote de empresas ou contatos (a chamada responde 200 mesmo assim). Corrija-os antes da produção
  • O endpoint de webhook verifica a assinatura e rejeita uma assinatura inválida
  • O receptor deduplica pelo id do evento (a ordem não é garantida e uma entrega pode se repetir)
  • Toda escrita envia Idempotency-Key
  • Foi testada uma nova tentativa com a mesma chave e não duplicou
  • O fluxo C completo funciona de ponta a ponta no sandbox
  • A fonte da verdade por entidade está combinada
  • Há um lugar onde o ERP registra os erros da API, com o request_id da resposta
  • Se o ERP tem IP fixo, ele está carregado na allowlist da credencial

A mudança para produção

  1. Peça à agência uma credencial hp_live_ da subconta real
  2. Troque a credencial e a URL do webhook
  3. Execute a carga inicial uma vez
  4. Verifique com GET /events que os eventos estão chegando

Não é preciso mudar mais nada. O sandbox e a produção usam a mesma API.
